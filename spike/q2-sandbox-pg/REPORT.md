# Q2 sandbox Postgres spike: report

Throwaway spike, never merged. See `../../q2-sandbox-pg-handoff.md` (scratchpad) for the brief.

## Verdict

**ADOPT_PG17.** Postgres 17 fits inside the Builder's E2B sandbox, starts well inside the Project
check's budget from a warm baked seed, and reproduces the Q1 arena's role-separation results
exactly against a plain Postgres 17 instance. PGlite's fallback path (step 5) was not needed.

## Template

Built under a separate name, never the pilot's: `conexus-q2-sandbox-pg`, template id
`ah3sn2s2449ypl0ukosd`, build `bfa2486b-0ec8-45d7-9f35-8f0415decceb`. Build time 35.8 s. Same base
image as the pilot Builder template (`node:24.20.0-bookworm-slim`), with `postgresql-17` from the
PGDG apt repo added, plus a warm data directory baked at build time via `initdb` as the
unprivileged `conexus-agent` (uid 1500). Size delta over the base image: +45 MB
(`/usr/lib/postgresql`), +39 MB (`/opt/conexus/pg-seed`, the baked seed).

## Start-time budget (`bench.sh`, `run-bench.mjs`, 10 runs each)

| path | median | p95 | min | max |
|---|---|---|---|---|
| fresh `initdb` + start + ready | 861 ms | 2990 ms | 723 ms | 2990 ms |
| warm (copy baked seed) + start + ready | 215 ms | 2232 ms | 192 ms | 2232 ms |

Both fit inside the Project check's budget; warm is 4x faster at the median and is what
`check-db.sh` uses. The p95 outliers (one run each) suggest occasional host contention, not a
Postgres-specific cost; still comfortably under a 10 s ceiling.

## Fidelity (`fidelity.sh`, `run-fidelity.mjs`, `docker-fidelity.mjs`)

Reproduced the Q1 arena's two-Project role shape (`provision.sql`, adapted from
`spike/q1-runner/provision.mjs` on `origin/spike/q1-runner-arena`): revoked `public`, one
schema-owning migrator role and one DML-only runtime role per Project, runtime search_path
pinned to its own schema. Applied the arena's migration
(`conexus/migrations/001_follow_up_note.sql`), ran its legitimate handler's SQL
(`handler-smoke.sql`), then ran its migration-attack and cross-project-attack cases
(`attacks-migration.sql`, `attacks-cross-project.sql`, generated by `gen-attacks.mjs` from the
arena's own attack lists).

Ran the identical SQL files two ways: inside a real sandbox built from the spike template
(`run-fidelity.mjs`), and against a disposable `postgres:17.10-bookworm` container started only
for this comparison (`docker-fidelity.mjs`, container name `conexus-q2-sandbox-pg-scratch`, torn
down after each run; the pilot's own `conexus-s7-postgres` container was never touched). The two
runs produced byte-identical `RESULT` lines: 9 of 12 attacks REFUSED at `42501` (permission
denied) in both environments, and the same 3 attacks succeeded in both:

- `mig_security_definer` and `mig_grant_cross` succeed because the migrator role owns its Project
  schema, and Postgres lets an object's owner create functions in it (including `SECURITY
  DEFINER`) and grant on it to any role. Neither is a sandbox artifact; both are inherent to
  "migrator owns its schema," present on any Postgres 17 with this role shape.
- `cross_search_path_b` succeeds because `SET search_path` is a session-local GUC change with no
  permission check; it only decides what an *unqualified* reference resolves to next. The arena's
  own `cross_project_sql.mjs` already excludes a successful `SET search_path` from its `BREACH`
  classification for this reason, and the real boundary tests, `cross_select_b` (read) and both
  `cross_set_role_*` (impersonation), both REFUSED at `42501` in both environments.

Sandbox and comparison agreeing exactly, including on these three, is the fidelity result: nothing
about running inside the E2B sandbox (unprivileged user, `/tmp` data directory, no listening
socket) weakens or strengthens Postgres's own privilege enforcement.

## check-db.sh

Prototype for the Project check: starts a disposable cluster from the warm seed, provisions one
Project's migrator/runtime role pair, applies `conexus/migrations/*.sql` in order as the migrator,
runs a smoke query as the runtime role, always stops the cluster, and always prints one JSON
verdict line so a caller can parse stdout unconditionally.

Proved live in the sandbox both ways (`run-check-db.mjs`, `run-check-db-failure.mjs`):

- Success: exit 0, `{"ok":true,"error":null,"migrationsApplied":["001_follow_up_note.sql"],"smokeOk":true,"elapsedMs":1021}`.
- Failure (a second migration referencing a nonexistent table): exit 1,
  `{"ok":false,"error":"psql:conexus/migrations/002_broken.sql:1: ERROR:  relation \"does_not_exist\" does not exist","migrationsApplied":["001_follow_up_note.sql"],"smokeOk":false,...}`,
  correctly stopping before the smoke step and reporting only the migration that did apply.

## Files

`template.mjs` recipe, `build.mjs` builds it, `bench.sh`/`run-bench.mjs` measure start time,
`provision.sql`/`conexus/migrations/001_follow_up_note.sql`/`handler-smoke.sql` are the arena
shape adapted to raw SQL, `gen-attacks.mjs` generates `attacks-migration.sql` and
`attacks-cross-project.sql` from the arena's own attack lists, `fidelity.sh`/`run-fidelity.mjs`
run them in the sandbox, `docker-fidelity.mjs` runs them against the disposable comparison
container, `check-db.sh` is the Project-check prototype, `run-check-db.mjs` and
`run-check-db-failure.mjs` prove its two exit paths live.

## Known gaps (spike scope, not blockers for the verdict)

- `check-db.sh` provisions a single Project's roles fresh each run; it does not yet address
  Project-to-Project isolation when several checks might run concurrently on the same host outside
  the sandbox (each sandbox is already isolated, so this is a non-issue for the real Project check,
  only for the shared `docker-fidelity.mjs` comparison path used in this spike).
- The bench and fidelity runs used one sandbox and one comparison container each; not repeated
  across a cold E2B host or under concurrent sandboxes, which the real Project check would need to
  characterize before relying on the p95 numbers here.
