# 0009. One failure table: one code, one row, one exit

**Date**: 2026-10-03
**Status**: Approved
**Lane**: `lane:shaped`
**Depends on**: nothing outside this repository. It lands before the spec that adds a question that
waits inside a run, which inherits its closed `FailureCode`.

References to "spike N" and to the census below name facts measured before the build, on a throwaway
branch that is not in this repository. Each slice proves again, in its own tests, the fact it
relies on.

Goal: every failure a person or operator can meet has one code, one category, one producer, one
person-facing message and action, and one log shape, defined in one place.

## 1. The shape and its one owner

Owner: `contracts/technical/failures.json`, beside `builder-run-vocabulary.json`, generated by
`scripts/generate-failures.mjs` with `--check` in CI. This is the same pattern the run vocabulary
already uses (P6), not a new one. One row per code:

| Field | Type | Why it is needed |
| --- | --- | --- |
| `code` | `UPPER_SNAKE` | The key. It is the log code, the wire code and Mastra's `id`. |
| `category` | `USER` \| `SYSTEM` \| `THIRD_PARTY` | Mastra's own `ErrorCategory` minus `UNKNOWN`. Who must act: the person, Conexus, or a vendor (model, E2B, company system). Replaces the `ours` flag thermo proposed, because `SYSTEM` already says it. |
| `status` | HTTP status, optional | Only for codes a route can return. A missing status means 500. |
| `audience` | `operator` \| `person` \| `person+app` | `operator` rows are logged only (boot, config). `person+app` rows also reach a generated app. |
| `message` | Portuguese, required unless `operator` | What happened, in the person's words. |
| `action` | closed union | `NONE`, `SIGN_IN`, `CONNECT_MODEL_ACCOUNT`, `ASK_ADMIN`, `ASK_CHANGE`, `CHOOSE_OTHER_MODEL`, `RETRY_LATER`. Each has one fixed Portuguese sentence. |

Derived, not stored: log level (`SYSTEM` error, `THIRD_PARTY` warn, `USER` info), problem type
(`urn:conexus:problem:<code>`), problem title (the code). No `domain`, `outcome`, `ours` or `title`
column: no consumer needs one that the fields above do not give.

Types and the generator do the checking. `FailureCode` is the union of the codes, and every throw,
`failBuilderRun`, `interruptBuilderRun` and broker refusal takes `FailureCode`, not `string`. The
Hub copy holds only code, category and status, so the generator's `--check` enforces the rest: a
`SYSTEM` row's `action` cannot be `RETRY_LATER`, a `SYSTEM` row's message says the failure was
recorded, and no `message` contains "tente", "novamente" or "de novo", so the only way to say "try
again" is the `RETRY_LATER` action.

Generated copies are needed because no shared import exists. The Hub, the web app and a generated
app are three builds, and `check-import-law.mjs` forbids cross-app imports. A generated app is a
separate Project. Each copy holds only what its build reads:

- Hub `apps/hub/src/platform/failures.generated.ts`: code, category, status. It sits in `platform/`, beside the `Failure` class that reads it, because the import law lets the HTTP layer reach only that module.
- Web `apps/web/src/generated/failures.ts`: code, message, action, for `person` rows.
- Generated app: the compiler template writes `app/src/conexus/failures.gen.ts` on every check
  and build, whether or not the app has a manifest. It holds the `person+app` rows and one
  fallback sentence with no retry wording. The starter's `errors.ts` imports it and no longer reads
  the code from the error's shape. It is a separate file because `api.gen.ts` is not written for
  an app with zero operations (spike 7a). Apps already built pick up the current text on their next
  build, and nothing is copied into Project source.

One thrown type: `class Failure extends MastraError` (installed `@mastra/core/error`), with
`id = code`, the row's `category`, `text = code`, and an optional `cause` and scalar `details`.
`npm ls @mastra/core` shows one copy, so `instanceof` holds.

Spike 1 showed the span records `id`, `category`, `domain`, `details` and `message`. `message` is
the code. Because `details` is exported to telemetry, it holds only our own identifiers: ids,
counts, a processor or config name. It never holds a secret, person text or vendor text. Review
checks it, and a `Readonly<Record<string, string | number | boolean>>` type keeps it scalar.

## 2. How a failure flows

1. **Raise.** Code throws `new Failure('PROJECT_BUSY')`. At a vendor boundary only (pg, E2B,
   Mastra, adapters, the runner reply), a catch turns a specific foreign error into a row.
2. **Convert once, log once.** `toFailure(error)` returns a `Failure` unchanged and wraps
   anything else as `INTERNAL_UNEXPECTED` (`SYSTEM`) with the original as `cause`.
   `logFailure(log, failure, fields)` writes one line through `recordFailure`, at the level the
   category sets, with `failure.code` and the trace id. It runs only where the failure leaves the
   process. That is one of four exits:
   - HTTP: Fastify's `setErrorHandler`, the only mapper. It checks `error instanceof Failure`
     first and looks up the row, because a `Failure` carries no `statusCode`. Next it maps
     Fastify's own errors through five rows keyed by `error.code`: `FST_ERR_VALIDATION`,
     `FST_ERR_CTP_BODY_TOO_LARGE`, `FST_ERR_CTP_INVALID_JSON_BODY`, `FST_ERR_CTP_EMPTY_JSON_BODY`
     and `FST_ERR_CTP_INVALID_MEDIA_TYPE`. Anything else goes through `toFailure`. It sends
     problem+json with `{type, title, status, code}`, plus `traceId` for `SYSTEM`. Its current
     `recordFailure('HTTP_SERVER_ERROR')` goes, so `logFailure` is the one line.
     `setNotFoundHandler` sends the `NOT_FOUND` row the same way, because an unknown route never
     reaches the error handler and today answers with Fastify's plain JSON (spike 3).
   - Mastra-mounted routes (`registerGuardedMastraMount`, `mastra-session-routes.ts:251`) hand
     requests to Mastra's own adapter, which may answer a handler error itself. Slice 1's test
     throws inside that mount. If Mastra answers first, the mount's guard converts that answer, and
     that guard is the only place that does. Slice 1 proved that Mastra answers first: a route's handler wraps a throw in an `HTTPException` that keeps the original's message and stack but not its identity, so a `Failure` thrown inside a Mastra handler arrives as `INTERNAL_UNEXPECTED`. `failureRoute` in `mastra-session-routes.ts` converts that, and sends it through an `HTTPException` carrying the problem+json response, which Mastra sends verbatim. Mastra's own 4xx refusals keep Mastra's shape until slice 2 gives them rows.
   - Run end: the settle path writes `toFailure(error).code` and logs it once. The two regex sites
     (`service.ts:152`, `run-runtime.ts:676`) and `BUILDER_PREPARATION_FAILED` as the catch-all
     code go.
   - Runner and MAR: the same problem+json body, so the third wire shape (`{error:{code}}`) goes.
     The MAR apps never throw today. They answer through local `refuse()` helpers
     (`application-host-routes.ts:86`, about 10 calls; `preview-routes.ts:201`, about 5 calls)
     and `refusal()` in `application-invoker.ts`. Each helper becomes `throw new Failure(code)`
     to the shared handler, and the helpers are deleted.
   - Boot: the process entry logs the `operator` row and exits.
3. **Show.** The web reads `code` from the problem body or the run's `failureCode`, and looks up
   `{message, action}` in its generated copy. `hubFetch` gains one `hubFailure(response)` that
   parses problem+json at the edge (P3). An unreadable body becomes the web row
   `HUB_RESPONSE_UNREADABLE`. A settled run with a `failureCode` shows the row's message. The
   status line keeps its own words only for success kinds (`Respondeu`, `Alterou o app`).

Mastra enters the table at the one boundary that already exists, `classifyAgentFailure` in
`builder/runtime.ts`. It becomes an exhaustive `switch` over code-sdk's 10 `ErrorType`s, so a new
Mastra type stops the build. `context_length` and `content_filter` get their own rows; today they
fall into `BUILDER_MODEL_STREAM_FAILED`. A non-retry `tripwire` becomes the `SYSTEM` row
`BUILDER_AGENT_TRIPWIRE`, with `processorId` in `details`. A `tool-error` is the model's to recover
from, so it never ends a run or reaches the person by itself.

A Conexus tool throws `Failure`. The model receives exactly the code as an `error-text` tool
result, and the run goes on (spike 6). Mastra wraps the throw in its own `MastraError`
`TOOL_EXECUTION_FAILED`, category `USER`, with our `Failure` as `cause`, and writes no log line. So
the one wrapper that builds Conexus tools calls `logFailure` on the way out, and anything that
reads a `tool-error` chunk reads `error.cause`, not `error.id`.

In the web transcript, `modelRetryNotice` stays: retry events carry `retryable`, `attempt` and
`max`, and they are not failures. `modelStoppedNotice` goes only after a browser check, run with
the existing flow tests, shows a failed run displaying its row message with no blank gap.
Spike 5 proved only that the turn rejects within about 2 ms of a terminal stream error. It did not
cover the Postgres write, `publishRun`, or the poll. Until that check passes, the terminal
`error` event stays handled in `transcript.ts`.

## 3. What it deletes, and what stays

Deletes (counts from the pre-build census):

- The Builder map: `failure-vocabulary.ts` (158 lines). That is `CATEGORY_BY_CODE` (82 keys, 32
  thrown codes missing), `CATEGORY_BY_PREFIX`, the 11-member category union and
  `projectBuilderRun`'s guess that an INTERRUPTED run was a cancel. Every INTERRUPTED writer
  already passes `HUB_RESTART` or `USER_CANCELLED` (`service.ts:338-340`).
- The web copy `failure-reasons.ts` (53 lines), with its 11 categories, 5 codes and
  `isBuilderFailureCategory`. Also the category tests in `run-state.ts:41-43`.
- Three error classes and their extractors: `ProjectError`, `WorkspaceError`,
  `IdentityAccessError` (80 lines), the `statusCode` smuggle in `host-sessions.ts:91` and the
  `IDENTITY_PROVIDER_UNAVAILABLE` branch in `http/app.ts:49`.
- `BROKER_ERROR_CODES` as a vocabulary. It becomes a subset typed `satisfies readonly FailureCode[]`.
- Route branching: 11 `.includes('CODE')` matches and their catch blocks in `builder/routes.ts`,
  the 6-branch status ladder in `http/app.ts:41-61`, 10 bare `reply.code(5xx).send()`. The 74
  hand-typed problem slugs become rows. The busy spellings (8), CSRF spellings (3) and
  authorization spellings (6) each collapse to one code.
- Web: 9 `*RequestError` classes, `delete-problem.ts`, `settings/error-messages.ts`, the status
  strings in `start-project.ts:19-25` and `entry-screens.tsx:48`, and the "tente/envie de novo"
  strings in 13 files.
- App side:
  - The starter's hand tables in `lib/errors.ts`: 12 messages, 2 fallbacks, and one code the
    runner never emits. They shrink to an import of `failures.gen.ts`.
  - Its shape-reading `codeOf` workaround.
  - The runner's `error.message.split(':')` at `app-runner/http.ts:35,69`.
  - The MAR `refuse()` and `refusal()` helpers.
- The 14 `MISSING_CONFIG_*` throws become one `operator` row, `CONFIG_MISSING`, with the name in
  `details`.
- The 8 `noEmptyBlockStatements` debt lines (section 4).

Stays, and why:

- `AdapterFailure` and `brokerCodeOf`. They are the adapters' own signal: `TOKEN_REFUSED` drives
  the token reissue. They live at the vendor boundary, and the mapping is a total `switch`.
- The `BrokerResult` value type. A handler reads a refusal as a value, not as a throw. Its `code`
  becomes `FailureCode`.
- The SQL `^[A-Z0-9_]{1,120}$` checks in three functions. They are the database's own boundary
  guard and list no codes, so they cannot drift. Removing them would only redefine three functions.
- `LOG_CODES` and its generator. They allowlist which log bodies leave for OTel, including the
  event lines, which are not failures. Typing those lines belongs to the telemetry spec (0007).
  Failure codes now have a real owner, so the derived list only follows it.
- `modelRetryNotice`. It is not a failure (section 2).

Net size: about 390 lines of whole files go, plus the route branches (about 100 by thermo's
count) and the web classes (about 250 by thermo's estimate). About 150 JSON rows and roughly 150
lines of TS come in (generator, `Failure`, handler). The diagnosis-only review measures the real
number.

## 4. Catches

- **Default: no catch.** A route or step that cannot handle a failure lets it reach its exit.
- **Map:** only at a vendor boundary, only for a named foreign condition (pg `23505`, `42501`,
  `AdapterFailure`, a Mastra `ErrorType`, an E2B exit code). Everything else is rethrown.
- **Log:** once, at the exit (`logFailure`). Never log and rethrow.
- **Swallow:** allowed only for best-effort work whose result has another path, and then it calls
  `logFailure`. Example: `publishRun`, where the poll still serves the run.
- **Enforcement:** Biome's `noEmptyBlockStatements` already fails an empty block. "A catch either
  rethrows, maps at a vendor boundary, or logs" becomes one line in
  `docs/development/review-checklist.md`, under Authority and design. This wave adds no new count
  or script: the Ratchets checks were deleted in #489. The census counts (74 bare `catch {`, 85
  `.catch` swallows) are what the slice 5 sweep works through. They are not a gate.
- **Broker** (thermo 02 F2): `broker.ts:124,190,240` map only `AdapterFailure` and
  `BrokerRefusal`. A store, envelope or code fault becomes the new `SYSTEM` row
  `CONNECTOR_PLATFORM_FAILED` and is logged. It no longer reads as `PROVIDER_UNAVAILABLE` with no
  log line. The envelope failure at `:131` stops calling itself `CREDENTIAL_REFUSED`.
- **The 8 debt lines.** Four are swallowed failures and get fixed:
  - `start-project.ts:37`: the chosen model is awaited, and its failure is shown.
  - `code-surfaces.tsx:19`: a failed language load sets plain text explicitly.
  - `postgres.ts:46`: the pool error is logged like the client error.
  - `egress-log.ts:290`: the second handler goes, and the race's catch already logs.

  The other four are not failures. They are no-op callbacks (`prompt-box.tsx:116`,
  `observability.ts:70`, `mastra-session-routes.ts:168,209`) and lose their suppression by making
  the prop or the initial value optional.

## 5. Person-facing messages

The table holds the messages. A subagent drafts every row in one pass, following one style
rule: what happened, in the person's terms, with no internal names. For `SYSTEM` rows the message
also says the failure was recorded. The operator reads the table once, as a sheet in the PR. Examples:

| Category | Code | status | message | action |
| --- | --- | --- | --- | --- |
| USER | `PROJECT_BUSY` | 409 | Este Project já tem um pedido em andamento. | `NONE` |
| USER | `MODEL_CREDENTIAL_REFUSED` | 422 | Nenhuma conta sua ou compartilhada atende este modelo. | `CONNECT_MODEL_ACCOUNT` |
| THIRD_PARTY | `MODEL_RATE_LIMITED` | 429 | O provedor do modelo está limitando os pedidos. | `RETRY_LATER` |
| THIRD_PARTY, app | `PROVIDER_TIMEOUT` | 504 | O sistema da empresa não respondeu a tempo. | `RETRY_LATER` |
| SYSTEM | `BUILDER_AGENT_STALLED` | none | O agente parou por uma falha do Conexus, não do modelo. As alterações desta execução não foram aplicadas, e a falha foi registrada. | `NONE` |
| SYSTEM, app | `CONNECTOR_PLATFORM_FAILED` | 500 | O Conexus falhou ao ler o sistema da empresa. A falha foi registrada. | `NONE` |
| operator | `CONFIG_MISSING` | none | (log only) | none |

(spike 4). Slice 3's generator prints every code that existed before the wave (the
`new Error('CODE')` literals and the old map's keys) and is not a row in the table. Each one gets a
target row, and the migration is an `UPDATE ... SET failure_code = CASE ...` over that list. Old
rows end on table codes, so the web needs no fallback for unknown stored codes.

## 8. Decisions

1. **What the person sees when Conexus itself fails.** What happened, that it was recorded, and a
   short reference (the run, or the first 8 characters of the trace id). No button and no "tente
   novamente", even after a Hub restart. The request text stays in the composer, so sending it again
   takes one click without the screen asking for it.
2. **Who writes the messages.** One pass under the frontend voice rule, and the operator reads the
   whole table once, as a sheet in the PR, before merge.
3. **Can the Builder change the failure texts of a generated app?** No. They come from the table
   through the generated client, so every app says the same thing and a rebuild updates them. An app
   shows its own words only for its own business rules.
