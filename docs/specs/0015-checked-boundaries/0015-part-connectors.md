It replaces the approved revision 3, which was written for the per command policy design and for amendment A+. ## Summary

Part 2 declares seven Connector operations, ports eleven SQL functions, parses its database rows, and splits both live Connector tables. A person reads them through two reader policies, and every Connector command runs on the command role after an admission. `listWorkspaceConnections` is a read that gives an installation administrator today's reach through the `reader_admin` policy. `createWorkspaceConnection`, `checkWorkspaceConnection` and `disableWorkspaceConnection` run in the administrator's own transaction after `admitInstallationAdministrator` with `connection.manage`. A person's read never sees a credential column. A workspace owner lists, binds and unbinds a project's connections under one new action, `connections.bind`, admitted through `admitProject`. The broker reads under the account that opened the Builder run, Preview or application, on the command role, filtered by the admitted Project. A Project member can use its open bindings through the broker before an application exists. An application grantee can use only open bindings of an application it may use. Both paths require an enabled Connection and an unarchived Project. Part 2 replaces the Connector purge function with a port in the existing Project purge transaction.

## 4. Reader policies and register rows

Both Connector tables have `ENABLE` and `FORCE ROW LEVEL SECURITY`, the command policy of the admission child, section 4.3, and the reader policies below. `A` is `(SELECT rls.acting_account())`, `ADMIN` is `(SELECT rls.acting_installation_administrator())`, and `OWNED(w)` is `w IN (SELECT workspace_id FROM iam.workspace_membership WHERE account_id = A AND role = 'owner')`. The membership subquery runs under that table's reader policy from part 0b, which calls a helper, so no policy reads its own table. Every branch requires `A IS NOT NULL`, and there is no system or grantee branch (rules 1 and 5 of the admission child, section 4.2). The broker and every Connector command read on the command role, so a person's `read()` needs only what `listWorkspaceConnections` and `listProjectConnectionBindings` list.

| Table | Policy | Predicate |
| --- | --- | --- |
| `connector.connection` | `reader` | `A IS NOT NULL AND disabled_at IS NULL AND OWNED(workspace_id)`. A Workspace owner sees the enabled Connections it may bind. |
| `connector.connection` | `reader_admin` | `A IS NOT NULL AND ADMIN`. Today's `listWorkspaceConnections` reach, disabled rows included. [0029_connector.sql:157](../../../apps/hub/migrations/0029_connector.sql#L157) |
| `connector.project_binding` | `reader` | `A IS NOT NULL AND unbound_at IS NULL AND OWNED(workspace_id) AND project_id IN (SELECT project_id FROM project.project WHERE archived = false)`. The Project subquery runs under part 3's reader policy, so a Project the person cannot see shows no binding. Only a Workspace owner reads a binding row. |

Neither policy reads the other table. Revision 3 let the binding policy read the Connection through `connector.enabled_connection`, a definer function, so that the Connection policy could read bindings without recursion. Both directions are now unneeded. The binding predicate does not test the Connection's `disabled_at`. `disableWorkspaceConnection` ends every open binding in the transaction that disables the Connection, so an open binding on a disabled Connection cannot exist, and every query that returns a Connection filters on `disabled_at IS NULL` explicitly. No fourth helper is needed. `ADMIN` appears only on the Connection policy, the one table of this part on the reach list of the admission child, section 4.2, rule 4. It is absent from binding `SELECT`, so an administrator without Project membership cannot call `listProjectConnectionBindings` or read bindings directly. A plain member reads no binding row through `read()`. It uses a bound Connection only through the broker, which reads on the command role after `admitProject` (section 5).
