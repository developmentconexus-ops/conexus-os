# 0015. Child: one data module, one receipt, one runtime role

Part of [spec 0015](index.md). Covers how the Hub reaches PostgreSQL: the only module that imports
`pg`, the transaction entries, the database error table, the idempotency receipt, the pools and the
database roles. Satisfies AC-5, AC-6, AC-10 and part of AC-14 of the umbrella.

## Summary

Every Hub statement goes through `apps/hub/src/platform/db.ts`, and every row it returns is parsed
by a Zod schema, so a row with the wrong shape is an error at the edge and not a lie inside. A
transaction always runs as a reader or a command role, and a read says who acts, which the reader policies use (see the admission child). Database
errors map to failure codes by SQLSTATE and constraint name, never by message text. One receipt table
replaces the three per owner. One login role, `hub_runtime`, replaces the capability roles; each
transaction switches it to `hub_reader` for a read or `hub_command` for a command (admission child,
section 4).

## 1. The module

`platform/db.ts` replaces `platform/postgres.ts` and is the only Hub file that imports `pg`.

```ts
export type Mode = 'read' | 'write'
export type Sql = { readonly [sqlBrand]: true; readonly text: string; readonly values: readonly unknown[] }
export type RawToken = Brand<string, 'RawToken'>   // a bearer token as presented; made only at the HTTP edge
export type Digest = Brand<Buffer, 'Digest'>       // made only by digest(raw)
type NoRawToken<V extends readonly unknown[]> = { readonly [K in keyof V]: V[K] extends RawToken ? never : V[K] }
export const sql: <V extends readonly unknown[]>(strings: TemplateStringsArray, ...values: V & NoRawToken<V>) => Sql  // every value becomes $n; a RawToken fails tsc; refused text throws (below)
sql.identifier: (name: string) => Sql                                              // quoted identifier

export interface ReadTx {
  readonly mode: Mode                                                     // 'read' here; the admission reads it to decide its lock
  readonly accountId: AccountId | null                                    // as built (db.ts:43): the read's account; null only in system and authenticate
  rows<S extends z.ZodType>(schema: S, query: Sql): Promise<readonly z.output<S>[]>
  one<S extends z.ZodType>(schema: S, query: Sql, missing: FailureCode): Promise<z.output<S>>
  maybe<S extends z.ZodType>(schema: S, query: Sql): Promise<z.output<S> | null>
}
export interface WriteTx extends ReadTx {
  readonly mode: 'write'
  run(query: Sql): Promise<number>                                        // affected row count
}

class Gate { readonly #gate = true }                                       // not exported: only db.ts constructs one
export type CommandGate = Gate                                             // no query method; an object literal or a spread copy fails tsc
type Actor =
  | { readonly kind: 'account'; readonly accountId: AccountId }            // transaction(accountId, fn)
  | { readonly kind: 'job'; readonly job: JobName }                         // system(job, fn)
  | { readonly kind: 'authentication'; readonly accountId: AccountId | null } // authenticate(fn): the account a lookup resolved, or none yet
class AuthGate {                                                           // not exported; a separate class, so no command admission accepts it. It carries no method: the lookups and steps are functions in identity-access/authentication.ts
  readonly #authentication = true
}
export type AuthenticationGate = AuthGate
const opened = new WeakMap<Gate | AuthGate, { readonly tx: WriteTx; actor: Actor }>()   // module private
export const openGate: (gate: CommandGate | AuthenticationGate) => { readonly tx: WriteTx; readonly actor: Actor }   // importable only by identity-access/admission.ts and identity-access/authentication.ts

export interface Database {
  transaction<T>(accountId: AccountId, fn: (gate: CommandGate) => Promise<T>): Promise<T>
  read<T>(accountId: AccountId, fn: (tx: ReadTx) => Promise<T>): Promise<T>
  system<T>(job: JobName, fn: (gate: CommandGate) => Promise<T>): Promise<T>
  authenticate<T>(fn: (gate: AuthenticationGate) => Promise<T>): Promise<T>   // part 6
  session<T>(fn: (lock: SessionLock) => Promise<T>): Promise<T>
  close(): Promise<void>
}
export const openDatabase: (connection: DatabaseConnection) => Database
export const openFactoryPool: (connection: DatabaseConnection) => FactoryPool   // the raw pool Mastra's PostgresStore takes
export const DATABASE_FAILURES: readonly DatabaseFailureRule[]
export type { ... }  // the pg types other modules name, re exported so none imports pg
type DatabaseConnection = { host; port; database; user: 'hub_runtime' | 'hub_factory'; passwordFile; max; options? }  // from platform/config.ts, as today; the transaction roles are not logins; options naming role is refused
type SessionLock = { readonly tryAdvisoryLock: (key: bigint) => Promise<boolean> }  // what platform/lifecycle.ts uses
type FactoryPool = Brand<pg.Pool, 'FactoryPool'>  // accepted only by the PostgresStore factory in builder/module.ts
```

There is no read without a schema: `rows`, `one` and `maybe` take one, and neither transaction type
has an untyped query. `WriteTx` is the only one with `run`, and a `ReadTx` is not assignable to it,
which part 0 proves with negative fixtures (a `run` on a read transaction, a read proof passed as a
write proof). A row that does not parse throws `ZodError`, which the error handler logs as
`INTERNAL_UNEXPECTED`. `one(schema, sql, missing)` throws `missing` as a `Failure` when there is no
row, so `rows[0]?.x as AccountId` has no place to live.

`transaction` and `system` hand their callback a `CommandGate`, and `authenticate` an
`AuthenticationGate`, never a `WriteTx`. The command role sees every row, so a statement before
admission would not be bounded by anything; the gate makes that statement impossible to write. A gate
is an instance of a class with a `#private` field that only `db.ts` constructs, so it is nominal like
the proof. `db.ts` records the gate's `WriteTx` and its actor in a module `WeakMap`, so the account or
the job travels once, from the entry to the admission. `openGate` returns that record and is imported
only by `identity-access/admission.ts` and `identity-access/authentication.ts` (a Biome restricted import with those two exceptions); the
`WriteTx` then reaches the command as `proof.tx`. A repository test lists the files allowed to call
`system` and `authenticate`.

**The authentication gate.** `authenticate` resolves a presented token before any account is known,
so it cannot bind an account up front. Its gate carries no method. Two closed families of functions in `identity-access/authentication.ts` run over it (HQ decision; reviews B and C, 2026-10-05), and each opens it with `openGate`, so identity SQL and identity types stay out of `db.ts`. The
first is `lookupByDigest(key)`, where `key` is a closed union with one member per kind: `{ kind, digest }`, except `{ kind: 'handoff', digest, projectId, bindingDigest }` for an application handoff and `{ kind: 'handoff', digest, host }` for a Preview handoff. Each kind names one table and its digest column, the query is
`WHERE <digest column> = $digest` plus the key's other values, it locks the one row it finds, and the digest is a `Digest`, never a
string. A lookup that finds an account records it as the gate's actor, so `admitAccount(gate)` then
reads it from there; `admitBootstrap(gate, digest)` locks the bootstrap context the same way. The
writes that follow (a session touched, an account created, the bootstrap receipt) run on `proof.tx`.
The second family is eight typed steps. Six run for what happens before any account or digest exists:
`lookupIdentity(issuer, subject)`, the account lookup at the OIDC callback; `provisionIdentity(claims)`,
which inserts the account and binds it as the gate's actor; `lookupSlug(slug)`, the application slug
lookup before any session; `hasOpenInvitation(email)`, the check for an open Workspace invitation to a
verified email; `startOidc(...)`, the state insert; and `mintContext(claims)`, the provisioning
context mint. Each is one exact statement keyed by one value, with no list. The claims are the values
the Hub read from the verified provider token, never from the browser. The gate offers no other query,
so an authentication flow cannot list or read by anything but a digest or one of these six values.
The other two, `consumeOidcState()` and `endCredential(reason)`, act only on the row a lookup of this gate bound, take no digest argument and need no active account.
Part 6 writes the closed key union (`DigestKey`) and the row types in that module, from the bodies it ports. A step that binds an account sets it on the record `openGate` returns.

**The tag refuses some text at run time.** Every `sql` call checks its composed text and throws
`INTERNAL_UNEXPECTED` with reason `SQL_TEXT_REFUSED` unless the text starts with `select`, `insert`,
`update`, `delete` or `with`, and on the bare word `conexus`, `session_authorization`, `u&`,
`set_config` or `current_setting` anywhere (admission child, section 4.1, has the exact rule and the
normalization). It guards against accidents in our own code, not against code written to evade it. `db.ts` sends `BEGIN`, the role switch and its settings on the client directly, so the
one place that must set them never builds them with the tag.

**No nested entries.** `db.ts` keeps an `AsyncLocalStorage` marker while an entry's callback runs.
Opening `read`, `transaction`, `system` or `authenticate` inside another's callback throws
`INTERNAL_UNEXPECTED` with reason `NESTED_TRANSACTION`. A nested entry holds one client while it
waits for another; with one pool of 20, twenty such callers would wait on each other forever. Work
that needs two transactions runs them one after the other (`createProject`, the project deletion).

**The entries.**

| Entry | Transaction | Statements after `BEGIN`, before `fn` | Used by |
| --- | --- | --- | --- |
| `transaction(accountId, fn)` | READ COMMITTED, read write | `SET LOCAL ROLE hub_command` | a person's command, an administrator's command, a grantee's checked or admitted read |
| `read(accountId, fn)` | REPEATABLE READ, READ ONLY | `SET LOCAL ROLE hub_reader`, then `set_config('conexus.account_id', $1, true)` | a person's read |
| `system(job, fn)` | READ COMMITTED, read write | `SET LOCAL ROLE hub_command`, then `set_config('conexus.job', $1, true)` | the jobs of `platform/jobs.ts`, the run executor, the project purge |
| `authenticate(fn)` | READ COMMITTED, read write | `SET LOCAL ROLE hub_command` | resolving a session cookie or a sign in to an account by digest, before the account is known (part 6) |
| `session(fn)` | none, one held client outside the pool | nothing; it runs only `pg_try_advisory_lock` as the login role | the instance advisory lock (`platform/lifecycle.ts`) |

The role switch is the first statement, a constant in `db.ts`. `LOCAL` makes the role and the setting
end with the transaction, so a client returns to the pool as `hub_runtime`, which holds no privilege
on a split table: after a commit, a rollback, or an error then a rollback, the next `SELECT` without a
role is 42501 (spike `authz-redesign/spike/spike.md:56-58`). With `false`, `set_config` leaked into
the next transaction on the same client (spike 3), and a bare `SET ROLE` survives a rollback
(`spike.md:63`), so neither exists outside the role lint's one allowance in `db.ts` (admission child,
section 4.1). Only `read` sets the account: no command policy reads it, and the command keeps its
account in the gate's actor and in the proof. Only `system` sets `conexus.job`, which the four purge
functions read as their guard (admission child, section 6); our code does not set it, and the tag refuses
the bare word `conexus` and `set_config`, which stops the accident. `system` may be called only by
`platform/jobs.ts`, the Builder executor module and `project/deletion.ts` (the purge and its
completion), and `authenticate` only by the session and sign in modules of `identity-access`. Both
are `Database` methods, so a repository test lists the files allowed to call each and fails on any
other. `authenticate` lands in part 6; until then the session store reads through `unportedPool`. A
Biome GritQL plugin refuses the text `set_config` or `conexus.` in any `sql` template outside
`db.ts`, the early warning for what the tag refuses at run time.

**Lifecycle of a transaction.** `BEGIN`, the role, the setting for a read, `fn`, `COMMIT`. On a throw, `ROLLBACK`; a
rollback that fails does not hide the original error, and a client that failed is discarded, not
returned to the pool (spike 2). After commit or rollback the `Tx` throws `INTERNAL_UNEXPECTED` with
reason `TRANSACTION_ENDED` on any use, so a proof kept past its transaction is dead. The per client
`error` listener of `platform/postgres.ts` moves into `db.ts`; without it a server disconnect crashed
the process (spike 2).

**Where `pg` may be imported.** Biome `noRestrictedImports` with `paths: { pg }` on `apps/**`, lifted
for `apps/hub/src/platform/db.ts` and for the application database edge of the app runner
(`app-runner/worker.ts`, `app-runner/supervisor.ts`). Those two files reach the generated
applications' own databases with each application's login, not the Hub database; their redesign
belongs to the Applications cluster wave, and the rule names them so a third file fails. The rule
fires on `import type` too (spike 2), which is why `db.ts` re exports the pg types. The other twelve
importers move off per part.

## 2. Database errors

```ts
type DatabaseFailureRule = { readonly sqlstate: string; readonly constraint: string | null; readonly failure: FailureCode }
```

`DATABASE_FAILURES` is one table. `db.ts` maps a `DatabaseError` by SQLSTATE and constraint name; a
rule with a constraint wins over one without (spike 2:
`workspace_membership_workspace_id_fkey` became `WORKSPACE_NOT_FOUND`, the cause kept). An unmapped
error is `INTERNAL_UNEXPECTED` with the cause. A test asserts that every constraint named in the
table exists in `pg_constraint` and every code exists in `failures.json`. No code reads
`error.message` of a database error; the five places that do today go with their owners
(`connectors/model.ts`, `identity-access/application-access.ts`, `builder/routes.ts`,
`builder/runtime.ts`, `identity-access/current-session.ts`). `toFailure`'s `P0001` branch
(`platform/failure.ts`) goes in part 6 with the last `RAISE`.

## 3. The receipt

One table, in a new schema `platform` owned by `conexus_owner`, both created in part 0:

```sql
CREATE TABLE platform.operation_receipt (
  operation_id   text        NOT NULL,          -- 'createWorkspace'
  authority      text        NOT NULL,          -- who may replay it: see below
  account_id     uuid        REFERENCES iam.account,  -- null only for the bootstrap authority
  key_digest     bytea       NOT NULL,
  request_digest bytea       NOT NULL,
  resource_id    uuid        NOT NULL,          -- the id reserved for what the command creates
  state          text        NOT NULL CHECK (state IN ('reserved', 'completed')),
  response_status smallint,
  response_body  jsonb,
  created_at     timestamptz NOT NULL DEFAULT now(),
  completed_at   timestamptz,
  PRIMARY KEY (operation_id, authority, key_digest),
  CHECK ((account_id IS NULL) = (authority LIKE 'bootstrap:%')),
  CHECK ((state = 'completed') = (response_status IS NOT NULL AND response_body IS NOT NULL AND completed_at IS NOT NULL))
);
```

`platform/receipt.ts` owns it:

```ts
type ReceiptScope = AccountScope | WorkspaceScope<WorkspaceAction> | ProjectScope | BootstrapScope
type DigestInput<O extends JsonOperation> = Pick<Input<O>, 'params' | 'query' | 'body'>   // what request_digest covers: everything but the key
type Receipt<I, R> = { readonly kind: 'fresh'; readonly resourceId: I } | { readonly kind: 'replay'; readonly reply: R }

// One transaction: reserve, run, store; a crash rolls back receipt and effect together.
export const idempotent: <O extends JsonOperation, I extends z.ZodType>(
  proof: Admitted<ReceiptScope>, op: O, key: IdempotencyKey, input: DigestInput<O>, id: I,
  run: (resourceId: z.output<I>) => Promise<Reply<O>>,
) => Promise<{ readonly replayed: boolean; readonly reply: Reply<O> }>

// Two transactions, for a command with an external effect between them (createProject).
export const reserve: (proof, op, key, input, id) => Promise<Receipt<z.output<I>, Reply<O>>>
export const complete: (proof, op, key, input, resourceId, reply: Reply<O>) => Promise<void>
```

`authority` is derived from the proof's scope, never passed: `account:<id>` for an account scope,
`workspace:<id>:account:<id>` for a workspace or project scope, `bootstrap:<issuer>:<subject>` for the
bootstrap scope. The same key sent by the same account to another workspace is a different receipt,
as today (`0001_baseline.sql`, the `createProject` key includes `workspace_id`). `request_digest` is the
canonical digest of the whole parsed input except the key (params, query and body), so a path id is
part of it. `id` is the brand schema of the reserved id (`WorkspaceId`, `ProjectId`); a stored
`resource_id` is parsed with it on replay, so no cast is needed. `response_status` is read on replay for
an operation with more than one success status.

The algorithm: insert the row as `reserved` with `ON CONFLICT DO NOTHING`, then select it
`FOR UPDATE` (a duplicate request waits for the first). A different `request_digest` is
`IDEMPOTENCY_CONFLICT`. A `completed` row is a replay, its body parsed with the operation's success
schema. A `reserved` row returns `fresh` with the stored `resource_id`, so a retry reaches the same id.
The digests use `packages/canonical-json`, as today.

**`createProject` (create project).** Transaction 1: admit the workspace, `reserve` (the project id is the
`resource_id`), commit. Outside any transaction: prepare the Git repository for that id, which is
idempotent by id, as today (`project/store.ts`, `repository.prepare`). Transaction 2: admit the
workspace again, lock the receipt `FOR UPDATE`; if it is `completed`, replay; else insert the project
and `complete`, commit. A retry after the account lost the workspace fails the second admission even
though a reservation exists. No admission lock is held across Git. This is today's sequence
(`project/store.ts`, `reserve` then `lock_create_project_receipt`) on the shared table.

**IAM-03 (operator bootstrap)** runs in `authenticate(fn)` before an account exists: `admitBootstrap`
locks the bootstrap context, found by the digest of the presented token, the receipt is reserved under
`bootstrap:<issuer>:<subject>` with no account, the account is created, and the receipt completes with
`account_id` still null. The receipt is on the command role and has no policy but the command one, so
no credential branch is needed. The reaper
deletes a bootstrap receipt with its expired context, as `0058_iam_reaper.sql` does today, now as a row
of `EXPIRY_RULES`. Workspace and project receipts do not expire, as today; project purge deletes the
receipts whose `resource_id` is the purged project.

**BLD create run keeps its own key.** A Builder run is deduplicated on the run row
(`builder_run_project_idempotency`), and a replay answers the run's current state, which the executor
reads to decide whether to start it. A stored first answer would replay a `QUEUED` run that already
ended. So BLD does not use this table; part 1 keeps the run row key and ports the replay as a read of
the current run.

The table replaces `workspace.operation_idempotency` (part 0), `project.operation_idempotency`
(part 3) and `iam.operation_idempotency` (part 6). Old receipt rows are not copied: a receipt is a
retry window, and this is a development database. A retry that spans the deploy of its owner's part
runs fresh.

## 4. Pools and roles

**One login role, two transaction roles.** `hub_runtime`: `LOGIN NOINHERIT NOBYPASSRLS`, a member
of `hub_reader` and `hub_command` and of nothing else, holding at the end no table or function
privilege of its own (during the parts, the direct grants of what no part has split yet, admission
child, section 7). `hub_reader`: `NOLOGIN NOBYPASSRLS`, `USAGE` on the Hub schemas and on `rls`,
`SELECT` on the tables with a reader policy, `EXECUTE` on the `rls` helpers. `hub_command`:
`NOLOGIN NOBYPASSRLS`, `USAGE` on the Hub schemas, the verbs and update columns the table register
names per table (`UPDATE (created_at)` on `iam.account`, since the admission takes it `FOR SHARE`, which needs an
update column, and revision 5.2 picks one with no rule on it; spike 2 measured the need with
`UPDATE (active)`), `EXECUTE` on the live functions a command entry calls and on
`iam.lock_administrators()`. None of the three has
`CREATE` anywhere, a grant on `factory` or Mastra storage, or membership in an owner role. Part 0b
creates the two transaction roles with the idempotent `DO` block of
`0062_runtime_data_boundary.sql:2-12` (roles belong to the cluster, so a second database on it may
already hold them) and grants them with
`GRANT hub_reader, hub_command TO hub_runtime WITH INHERIT FALSE, SET TRUE` (PostgreSQL 16 and later
record inheritance per membership; the cluster is 17), and `ADMIN` is never granted. Spike 2
recorded `42501` for the login role on CREATE TABLE, CREATE SCHEMA, ALTER, DROP, TRUNCATE, CREATE
FUNCTION, SET ROLE to another role and any read of `factory`; the split spike recorded `42501` for
`SET ROLE postgres` (`authz-redesign/spike/spike.md:45`).

`hub_factory` stays as it is, for Mastra storage (`builder/module.ts`, `max: 20`). `openFactoryPool`
is the one export of a raw pool, typed so only `@mastra/pg`'s store accepts it; Mastra parses its own
rows, and census rule 1 names this export as its single exception.

**The policy helper role.** `iam_rls`: `NOLOGIN NOINHERIT NOBYPASSRLS`. It owns the three
`rls.acting_*` functions and has `SELECT` on the rows they read (see the admission child, section
4.2). It exists because a membership policy cannot read its own table (42P17, spike 3).

**One pool.** The Hub opens one `Database` as `hub_runtime`, plus the `hub_factory` pool for Mastra.
The two transaction roles share it; a switch costs one statement per transaction and no connection.
The ten pools over nine capability roles become one in part 0, and the capability roles are dropped
in the part that ports the last function granted to them (each part removes its own grants and its
`ROLE_BY_CALL_SITE` rows in `tests/repository/hub-call-sites.mjs`). The pool has `max: 20` (ten pools
of up to 6 today); the advisory lock of `session` holds its own client outside the pool, so a full pool
cannot starve it. The executor pool handed to the
application host (`hub.ts:129-137`) goes in part 0; `registry/served-application.ts` reads inside
`read(accountId, ...)` through the unported `reg` functions until part 4, then filtered by the admitted project after
`checkApplication` on the command role (admission child, section 6).

**Object owners.** The seven NOLOGIN `*_owner` roles keep owning their objects while their definer
functions live, since a `SECURITY DEFINER` function runs as its owner. Part 0 creates the NOLOGIN role
`conexus_owner` to own the `platform` schema (the `%_owner` rule of `assertRoleInvariants` already
requires NOLOGIN; a `hub_` name would fail the LOGIN rule). Part 6 moves every Hub object to it and
drops the seven. Migrations keep running on the connection provisioning gives them today, the
database superuser, which bypasses Row Level Security even under `FORCE`; a migration that moves rows
needs nothing more.

**The register.** `contracts/technical/hub-database-roles.json` stays the one register: part 0 adds
the `hub_runtime` row and a `policyRoles` list with `iam_rls`, part 0b adds the `hub_reader` and
`hub_command` rows as transaction roles and points `policyRoles` at the three `rls` helpers, and each
part deletes the rows it retires. `scripts/generate-hub-role-register.mjs`, provisioning and
`docs/reference/hub-database-roles.md` follow from it. `assertRoleInvariants`
(`scripts/hub-catalog.mjs`) keeps "every `%_owner` role is NOLOGIN". Its rule "every `hub_*` role is
LOGIN NOINHERIT" becomes "every login role of the register (`hub_runtime`, `hub_factory`) is LOGIN
NOINHERIT, and every transaction role (`hub_reader`, `hub_command`) is NOLOGIN". It gains: `iam_rls`
is NOLOGIN, not BYPASSRLS, owns exactly the helpers the register's `policyRoles` row lists, and holds
only `SELECT`; no role but the owner roles still listed owns a Hub object; `hub_runtime` is a member of
exactly `hub_reader` and `hub_command`, and they of no role; both of those memberships have
`inherit_option = false` and `admin_option = false` in `pg_auth_members`; `pg_db_role_setting` holds
no `role` or `session_authorization` setting for `hub_runtime`, for the Hub database, or for the pair.
`openDatabase` refuses a `DatabaseConnection` whose `options` names `role` or `session_authorization`
(`db.ts:16` carries `options`, which `builder/module.ts:141` uses for `search_path` on `hub_factory`,
so the refusal is by content, not by presence). The `publicExecutable` check's schema list gains
`platform` and `connector` (it omits `connector` today). The check that refuses `BYPASSRLS` stays.

**Dropping a role.** Roles belong to the cluster, not the database, and `DROP ROLE` answers 2BP01
while another database on the cluster still grants to it (`docs/reference/hub-database-roles.md`). A
part's migration revokes everything from a retired role and drops it when nothing else holds it; the
done state is "no grant, no ownership and no login by a retired role in this database, and none in
`pg_roles` on a fresh cluster". Removing a leftover role from a shared cluster is an operator step, as
it is today.

## 5. A store, after

`workspace/store.ts`, part 0 (spike 2 measured the module at 208 lines before, 161 after):

```ts
const WorkspaceRow = z.object({ workspace_id: WorkspaceId, name: WorkspaceName })

export const workspaceStore = (database: Database) => Object.freeze({
  list: (accountId: AccountId) => database.read(accountId, (tx) =>
    tx.rows(WorkspaceRow, sql`SELECT workspace_id, name FROM workspace.workspace ORDER BY name`)),

  create: (accountId: AccountId, key: IdempotencyKey, body: Input<typeof createWorkspace>['body']) =>
    database.transaction(accountId, async (gate) => {
      const creator = await admitAccount(gate)
      return idempotent(creator, createWorkspace, key, { params: undefined, query: undefined, body }, WorkspaceId, async (workspaceId) => {
        await creator.tx.run(sql`INSERT INTO workspace.workspace (workspace_id, name) VALUES (${workspaceId}, ${body.name})`)
        await grantCreatorMembership(creator, workspaceId)
        return { workspaceId, name: body.name, creatorAccountId: accountId, initialAccessEstablished: true }
      })
    }),
})
```

`list` has no `WHERE`: it runs as `hub_reader`, and the reader policy shows only the acting account's
workspaces. `create` runs as `hub_command`; what it may write is decided by `admitAccount` and by
`grantCreatorMembership`, which founds only a workspace with no membership (admission child, section 3).

## 6. Value sourcing

| Action | Value | Source |
| --- | --- | --- |
| every transaction | the role | the entry: `hub_reader` for `read`, `hub_command` for the others, a constant in `db.ts` |
| a read transaction | `conexus.account_id` | the `accountId` argument, parsed from the session |
| a command transaction | the gate's actor | the `accountId` argument of `transaction`, parsed from the session; read by the admission, never passed again |
| a job transaction | the gate's actor and `conexus.job` | the `job` argument of `system`, one of the closed `JobName` list |
| a token lookup | the `Digest` | `digest(raw)` of the `RawToken` parsed at the HTTP edge |
| `one` | the failure when no row | its `missing` argument |
| a mapped database error | the failure code | `DATABASE_FAILURES` by SQLSTATE and constraint |
| a receipt | `key_digest`, `request_digest` | canonical JSON digest of the header key, and of the parsed params, query and body |
| a receipt | `authority` | the proof's scope (account, workspace with account, or bootstrap issuer and subject) |
| a receipt | `resource_id` | `id.parse(randomUUID())` once, then the stored row parsed by `id` |
