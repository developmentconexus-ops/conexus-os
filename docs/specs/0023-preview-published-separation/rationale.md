# 0023. Rationale for Preview and Published separation

## Context

The accepted investigation identifies one shared allocation and a Registry reader of the Builder Preview pointer as the reasons build/tests can affect the employee application. Integrated boundaries moved source and authority contracts to their native owners but deliberately left the pointer exception for Q5. Applications backup is now integrated; replacing it or claiming cross-cluster atomic recovery would discard established evidence.

The recorded operator choices are owner publication, one act creates immutable Release, owned Published data starts empty, synchronization later, one shared read-only Connection and refusal of deletion while published. No real apps were recorded as in use. This proposal implements the first separation step only, under delegated technical acceptance by Firstmate.

## Options considered

### Retain Preview as the employee application with a Published flag

Small changes would preserve current routes and add conditionals to runner, broker and data plane. However, a flag beside the old Preview pointer would keep build as publication, retain two owners of the same fact and leave reset authority easy to confuse. It fails explicit-publication meaning and domain typing. Rejected.

### Create a mutable Published artifact pointer now

Employee routes could select another artifact and use another schema before Release exists. That would introduce a publication transition with no explicit owner act and then require replacement in stage2. Tests might be green while protecting unapproved temporary meaning. Rejected.

### Separate domains and require real publication before employee serving

The runner owns distinct allocation variants and permits Preview reset only. Registry owns Preview coordinates in the same settlement transaction. Stage1 removes employee access to Preview entirely and uses the existing unavailable outcome; stage2 later installs a real Release consumer. One Project binding reflects the approved shared Connection without duplicated environment records. This is the smallest adequate design that deletes accidental authority rather than adding flags. Recommended.

## Decision and why

This is a proposed technical design, not self-approval. Firstmate must accept the exact proposed commit before product implementation. Product choices are inherited from the recorded operator statements and are not reopened. The task explicitly authorizes direct-PR delivery into the foundation, one independent reviewer per batch and no worker merge, replacing generic wave/main publication instructions for this task.

Redesign from First Principles removes automatic employee serving. Model the Domain separates allocation authority and EMPTY/READY Registry state. Migrate Callers Then Delete Legacy APIs removes the Builder pointer and employee Preview readers with all consumers. Subtract Before You Add removes the duplicated binding axis. Prove It Works requires actual native schema/ACL/ledger behavior, not signature compilation alone.

## Evidence and references

The planning session holds the bounded study reconciliation, consumer discovery census, native allocation probe, executable Zod shape probe, fresh Hub build and prior independent boundary/backup reviews. Their exact source pins, commands and limits are recorded in the study/checkpoint. Public references and inspected native file lines appear in index.md. Missing inherited Appwrite/Rails/SupabaseCLI/Kamal repositories are explicitly unverified here; no new mechanism depends on their assumed APIs.

The old per-file migration suggestion contradicts the native batch contract, so it is dropped. The suggestion that expand-only always makes old code compatible is unproved. Later stages must prove compatibility and idempotent convergence across independent clusters. This proposal does not authorize real-data migration or destructive recovery.
